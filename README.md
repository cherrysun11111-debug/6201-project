# E-commerce Complaint Risk Analysis

This project detects complaint risk in e-commerce reviews and support messages. The primary user is a small marketplace support lead who needs to triage risky complaints before they become refund disputes, safety incidents, or public reputation problems.

## Problem

Small e-commerce teams receive many short customer reviews and support messages. A support lead reviewing even 100 messages per day has only seconds to decide which cases need escalation, and a missed safety or refund complaint can become a chargeback, public escalation, or repeat support contact. The business problem is not general sentiment analysis; it is identifying which messages need faster human attention. The system classifies each review as `low`, `medium`, or `high` risk, identifies the likely complaint type, extracts evidence terms, assigns an SLA, and returns a response frame for the support team.

Closest existing tools include Zendesk, Shopify Inbox, Gorgias, and marketplace review dashboards. Those tools manage tickets and conversations, but this project focuses on a transparent, local, evaluated risk triage queue that compares against a non-AI baseline and can run without sending customer text to a hosted service.

Out of scope: automated refunds, final customer replies, legal decisions, and safety-critical decisions without human confirmation.

## AI Choice

The current AI decision is narrow machine learning plus deterministic rules:

- A keyword baseline for comparison.
- A pure Python multinomial naive Bayes model for risk classification.
- Deterministic abstention when confidence is below threshold.
- Rule-based complaint type detection for transparent explanations.

This is intentionally not an agent: the task is bounded classification and routing, not autonomous multi-step tool use. It also intentionally does not put an LLM/RAG layer in the current decision path, because refund and safety triage needs auditable behavior, stable local cost, and reproducible evaluation. A future LLM/RAG layer would be rented only for policy-grounded response drafting, not for final risk decisions.

## Data

The project uses a reproducible synthetic dataset generated by `src/ecrisk/data.py`. Default size is 420 rows, with labels for risk and complaint type. Synthetic data is appropriate for the first four-week build because it avoids personal data and can be regenerated exactly with a seed.

The repository also includes `data/challenge_reviews.csv`, a 40-row hand-written set of ambiguous reviews used to expose the ceiling of synthetic training data.

Future real-data option: Amazon Customer Reviews Dataset or a merchant's consented support exports. If real customer data is used, private data must be excluded from the public repository.

## Evaluation

Primary metric: macro F1 across `low`, `medium`, and `high` risk.

Baseline: keyword rules in `src/ecrisk/baseline.py`.

Target: model macro F1 of at least 0.90 on the synthetic held-out split, plus a separate challenge-set score that is expected to be lower and more realistic. Abstention is reported separately.

The evaluation also includes a leakage probe that masks obvious risk and complaint keywords before re-running the model. This checks whether performance depends too heavily on shortcut words such as `refund`, `fake`, or `tracking`.

## Run

From this folder:

```powershell
$env:PYTHONPATH="src"
python -m ecrisk.data --rows 420 --seed 6201
python -m ecrisk.train
python -m ecrisk.evaluate
python -m ecrisk.batch
python -m ecrisk.predict "The seller refused my refund and I may file a chargeback"
python -m ecrisk.app
```

Then open `http://127.0.0.1:8000`.

On Windows PowerShell, the same workflow can be run with:

```powershell
.\scripts\run_pipeline.ps1
.\scripts\run_demo.ps1
```

On macOS, Linux, or any machine with Python 3.10+, use the cross-platform scripts:

```bash
python scripts/run_pipeline.py
python scripts/run_demo.py
```

The web demo has two views:

- Single review: one customer message in, detailed triage result out.
- Priority queue: batch analysis of the sample CSV, sorted by high-risk complaints first.

## Responsible Use

Risks and mitigations:

- Silent failure: a high-risk complaint may be labelled medium or low. Mitigation: compare against baseline, report confusion matrix, and route low-confidence cases to human review.
- Over-automation: the tool may be used as a final decision maker. Mitigation: output action recommendations only; do not trigger refunds or penalties.
- Synthetic-data ceiling: generated reviews may be narrower than real customers' language. Mitigation: keep generator code committed and validate later on consented real examples.
- Privacy: real reviews may contain personal data. Mitigation: do not commit raw customer data; anonymize and document consent or source license.

## Project Requirements Mapping

- One problem: triage complaint risk in e-commerce reviews.
- One primary user: marketplace support lead.
- Named data source: generated dataset in `data/reviews.csv`, 420 rows by default.
- Named baseline: keyword classifier.
- Named metric: macro F1 with baseline comparison.
- Smallest first version: one review in, one classifier call, one risk label and action out.
- Current enriched version: one review in, one risk label, complaint type, evidence terms, SLA, response frame, and responsible-use note out.
- Repository portability: standard library implementation, no required external ML dependencies.

## Current Results

Latest generated evaluation:

- Synthetic held-out split: model macro F1 `1.000`, keyword baseline macro F1 `0.907`.
- Challenge set: model macro F1 `0.675`, keyword baseline macro F1 `0.454`.
- Leakage probe after masking obvious risk keywords: model macro F1 `0.550`, keyword baseline macro F1 `0.144`.
- Challenge-set abstention: `3/40` cases, and `2/3` abstained cases would otherwise have been wrong.
- Interpretation: the synthetic split confirms the pipeline works; the challenge set and leakage probe are the more honest demos of generalization risk.
