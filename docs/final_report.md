# Final Report

## Project Outcome

ComplaintRisk Queue is an end-to-end triage system for small e-commerce support teams. The project addresses one practical problem: a support lead may receive many reviews and support messages each day, but not every negative message has the same urgency. A late-delivery complaint, a wrong-size item, a refund dispute, and a product-safety warning should not be handled in the same order. The system makes the support workflow different from today by turning an unordered review queue into a risk-prioritized queue with evidence terms, complaint type, SLA guidance, and a human-review warning.

The current product has two demo modes. The single-review view accepts one customer message and returns a low, medium, or high risk label, complaint type, confidence, evidence terms, recommended action, customer reply frame, and responsible-use note. The priority-queue view analyzes the sample CSV and sorts the highest-risk cases first so the support lead can start with safety, counterfeit, refund, delivery-loss, and severe service-failure complaints.

## Design Reasoning

I deliberately did not frame the project as general sentiment analysis. Sentiment alone does not tell a support lead what to do next. A polite message about a swollen battery is more urgent than an angry message about slow delivery. The project therefore predicts complaint risk, not mood.

I also chose a narrow machine learning classifier rather than an autonomous agent or a foundation-model-first design. The task is bounded: classify short text into low, medium, or high risk, then route it. A multinomial naive Bayes classifier is simple, auditable, cheap, and local. Deterministic rules add complaint type, evidence terms, SLA, and escalation logic. A keyword baseline is included because a non-AI method is the right first comparison. If simple rules were enough, a more complex model would not be justified.

I did not connect LLM/RAG in the current decision path. Refund and safety triage should be reproducible and inspectable during evaluation. A future LLM/RAG layer would be useful for policy-grounded response drafting, but it should not make final safety or refund decisions.

## Data And Evaluation

The repository includes a reproducible 420-row synthetic dataset generated by `src/ecrisk/data.py`. It also includes a 40-row hand-written challenge set with mixed sentiment, typos, weak signals, and ambiguous cases. This split is intentional: the synthetic set verifies that the pipeline works; the challenge set tests whether the model survives less tidy language.

The primary metric is macro F1 across low, medium, and high risk. Macro F1 is better than accuracy because the business value depends on catching high-risk complaints without ignoring medium and low cases. The keyword baseline is implemented in `src/ecrisk/baseline.py`.

Current results show a useful but imperfect system. On the synthetic held-out split, the model reaches macro F1 of 1.000 while the keyword baseline reaches 0.907. This confirms that the pipeline works, but it is not the most honest estimate of real performance because the data is generated from known templates. On the challenge set, the model reaches 0.675 while the baseline reaches 0.454. The model still improves over the baseline, but the gap between synthetic and challenge performance reveals the project’s main limitation: real customer language is harder than generated examples.

I also ran a leakage probe by masking obvious words such as refund, fake, tracking, and sparked. After masking, the model reaches macro F1 of 0.550 while the baseline drops to 0.144. This suggests that the model learns more than direct keywords, but strong lexical signals still matter. That is a useful critique rather than a failure: it shows where future data collection should focus.

## Responsible Use And Limitations

The main silent failure is a high-risk complaint being labelled low or medium. This could affect customers waiting for refunds, buyers exposed to unsafe products, or sellers facing public escalation. Mitigations include confidence reporting, confusion matrices, a challenge set, leakage probe, and abstention. On the challenge set, the system abstains on 3 of 40 cases, and 2 of those 3 would otherwise have been wrong. This is small but meaningful evidence that abstention can catch some risky uncertainty.

The system is explicitly not allowed to automatically issue refunds, penalize sellers, remove listings, or make safety decisions. It is a triage aid only. A human support lead remains responsible for sensitive cases.

The largest limitation is data realism. Synthetic data makes the project privacy-safe and portable, but it cannot fully represent real customer language. The challenge set partly addresses this, but 40 rows is still small. The project should not be treated as deployable until evaluated on consented or public real review data.

## Difficulties And Tuning

The first version had an overly simple single-review interface and overly clean data. I expanded the demo into a batch priority queue because that better matches the support lead’s workflow. I also added data variation, a challenge set, leakage testing, abstention metrics, and cross-platform run scripts. Another rough edge was the priority queue summary: it initially calculated distribution over the displayed top 25 rows, which made the queue look like all examples were high risk. I corrected it so the summary is based on all 420 analyzed rows while the table shows only the top-priority slice.

## Future Path

The next step is to add real data from a licensed public review dataset or consented merchant export. I would then add a retrieval layer over store return, delivery, and safety policies, and rent an LLM only to draft policy-grounded response suggestions with citations. I would also add human feedback capture so support leads can correct predictions and build a stronger evaluation set over time.
