# Final Report

## What I Built

ComplaintRisk Queue is a small end-to-end system for triaging e-commerce complaints. I chose this problem because a support lead does not only need to know whether a customer is unhappy; they need to know which message should be handled first. A slow-delivery complaint, a wrong item, a refund dispute, and a product-safety warning all look like negative feedback, but the business response is different.

The current demo has two modes. The single-review page takes one customer message and returns a risk level, complaint type, confidence score, evidence terms, SLA guidance, recommended action, and a responsible-use note. The priority-queue page runs a batch of reviews and shows the highest-risk cases first. That second view became important because it better matches the real workflow: a support lead usually starts with a queue, not one isolated review.

## Reasoning Behind The Design

I deliberately avoided building a generic sentiment classifier. Sentiment is too broad for the problem. A polite message about a swollen battery can be more urgent than an angry message about a delayed parcel. I wanted the output to connect directly to an operational decision: standard queue, support follow-up, or human escalation.

I also kept the model intentionally simple. The implemented classifier is a multinomial naive Bayes model written with the Python standard library. I paired it with deterministic rules for complaint type, evidence terms, SLA, abstention, and human-review guardrails. This choice is not the most glamorous model choice, but it made the system portable, inspectable, and easy to compare against a keyword baseline. For this project, that mattered more than using a heavier library or a hosted model.

I did not put an LLM or RAG system in the current decision path. My reason is that refund, counterfeit, and safety triage should be reproducible during evaluation. A future LLM/RAG layer could be useful for drafting a policy-grounded customer reply, but I would not want it to be the component deciding whether a safety complaint is high risk.

## Data And Evaluation

The main dataset is a reproducible 420-row synthetic dataset generated by `src/ecrisk/data.py`. I also wrote a 40-row challenge set by hand. The challenge set includes mixed sentiment, typos, weak signals, and ambiguous complaints because the first synthetic dataset was too clean.

The primary metric is macro F1 across low, medium, and high risk. I used macro F1 instead of accuracy because the system should not look good by only handling the easiest or most common class. The baseline is a keyword classifier in `src/ecrisk/baseline.py`.

The results tell a more honest story when read in three parts. On the synthetic held-out split, the model reaches macro F1 of 1.000 and the baseline reaches 0.907. This proves the pipeline works, but it is not enough evidence by itself because generated data can match the generator too closely. On the challenge set, the model reaches 0.675 while the baseline reaches 0.454. That lower number is useful: it shows the model still beats the baseline, but it is not ready to be treated as deployment-grade.

I also added a leakage probe. I masked obvious words such as refund, fake, tracking, and sparked, then evaluated again. The model drops to 0.550 while the baseline drops to 0.144. This confirmed one suspicion: the model is not only memorizing direct keywords, but it still relies heavily on strong lexical signals. If I continued this project, I would focus data collection on paraphrases and cases where urgency is implied rather than stated.

## Responsible Use And Limitations

The main silent failure is a high-risk complaint being labelled low or medium. That could affect customers waiting for refunds, buyers exposed to unsafe products, or sellers facing public escalation. I added confidence reporting, confusion matrices, a challenge set, leakage testing, and abstention to make that risk visible. On the challenge set, the system abstains on 3 of 40 cases, and 2 of those 3 would otherwise have been wrong. That is not a complete safety solution, but it shows that abstention can catch some uncertainty instead of forcing a guess.

The system is not allowed to automatically refund, penalize sellers, remove listings, or make safety decisions. It only helps a human support lead decide what to inspect first.

The biggest limitation is data realism. Synthetic data made the project portable and privacy-safe, but real customer language is messier. The challenge set helped expose this, but 40 rows is still small. I would not claim this project is ready for production without real, consented or licensed data.

## What Changed During The Build

The first version was too narrow: it only handled one review at a time, and the evaluation looked unrealistically strong. I added the batch priority queue, challenge set, leakage probe, abstention metrics, and cross-platform scripts after seeing those weaknesses. I also fixed a misleading queue summary that originally calculated distribution over only the displayed top 25 rows. Now the page summarizes all 420 analyzed rows while showing only the top-priority slice.

## Future Path

The next step is better data. I would add a licensed public review dataset or a consented merchant export, then compare performance before and after real data. After that, I would add retrieval over store return, delivery, and safety policies. An LLM could draft customer-response suggestions with citations to those policies, but the risk routing should stay local and auditable. I would also add a feedback button so support leads can correct predictions and build a stronger evaluation set over time.
