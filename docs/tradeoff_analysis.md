# Business And Technical Trade-Off Analysis

I chose e-commerce complaint triage because it has a clear user and a clear operational decision. A support lead at a small store may need to scan around 100 customer messages in a day. Even a quick 30-second scan per message takes almost an hour before any actual resolution work starts. More importantly, missing a safety, counterfeit, refund, or delivery-loss complaint can lead to a chargeback, repeat contact, or public escalation.

The closest existing tools are Zendesk, Shopify Inbox, Gorgias, and marketplace review dashboards. They are useful for managing conversations, but they do not give me the kind of transparent, inspectable project I need here: a local triage queue with a named baseline, reproducible data, challenge cases, leakage checks, and explicit evaluation. So the gap is not "customer support has no tools"; the gap is a small auditable risk-ranking system that can be understood end to end.

The simplest baseline is a keyword rule set. It flags words such as refund, chargeback, fake, sparked, tracking, missing, and support. I kept this baseline because it is cheap, fast, and easy to explain. It is also a useful reality check: if the model cannot beat this, the model is not earning its place. The weakness is that keywords are brittle. They miss typos, paraphrases, mixed sentiment, and cases where urgency is implied indirectly.

The model I implemented is a multinomial naive Bayes classifier in pure Python. This is a narrow machine learning choice for a bounded prediction problem: classify complaint risk as low, medium, or high. I chose it because it runs locally, has no API cost, and is easy for a TA or agent to inspect. I gave up some modelling power compared with transformer classifiers, but I gained portability and reproducibility.

The data strategy is also a trade-off. The 420-row synthetic dataset is reproducible and privacy-safe, which is useful for a coursework repository. But synthetic data can be too neat, so I added a 40-row hand-written challenge set with typos, weak signals, and mixed sentiment. The results show the difference clearly. On the synthetic held-out split, the model reaches macro F1 of 1.000 and the keyword baseline reaches 0.907. On the challenge set, the model reaches 0.675 while the baseline reaches 0.454. The challenge score is less flattering, but more believable.

I also ran a leakage probe by masking obvious risk words such as refund, fake, tracking, and sparked. After masking, the model reaches 0.550 and the baseline falls to 0.144. This tells me the model is not only matching direct keywords, but it still depends on strong lexical clues. That is a rough edge I would not hide in the final report.

I did not connect an LLM or RAG layer in the current decision path. A hosted LLM could make the response text sound better, and RAG over store policies would be useful later. But for refund and safety triage, I wanted the decision path to be auditable, cheap, and reproducible. My future design would rent an LLM only for policy-grounded response drafting, while keeping risk classification and escalation local.

The build-versus-buy split is therefore layer by layer. I own the local web interface, orchestration scripts, data generator, challenge set, baseline, classifier, abstention logic, leakage probe, batch queue, and reports. I currently rent nothing, so the project has no per-call API cost and no customer text leaves the machine. In a later version, I would rent an embedding model or LLM for policy retrieval and response drafting, but only after measuring cost, latency, and privacy trade-offs per review.

The biggest risk is silent failure: a high-risk complaint is labelled low or medium and the support lead misses it. My mitigations are confidence reporting, confusion matrices, challenge evaluation, leakage testing, and abstention. On the challenge set, 3 of 40 cases abstain at the current threshold, and 2 of those 3 would otherwise have been wrong. That is not enough for production, but it is a useful sign that uncertainty handling is doing real work.
